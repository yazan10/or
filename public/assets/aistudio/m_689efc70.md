# البرومبت الرئيسي الشامل لمنصة تحليل التسويق بالذكاء الاصطناعي
## وثيقة توجيه OpenCode لبناء منصة SaaS كاملة

> **طريقة الاستخدام:** أعطِ هذا الملف إلى OpenCode بعد تثبيت الـ Skill الخاصة بالمشروع. اطلب منه أولاً قراءة الوثيقة وتحويلها إلى خطة تنفيذ ومراحل، ثم تنفيذ المشروع مرحلةً بعد مرحلة. لا تتجاوز بوابات التحقق ولا تستبدل المتطلبات بقرارات افتراضية من عندك.

---

# 1. دورك والهدف

أنت مهندس برمجيات Full‑Stack ومهندس منتجات SaaS ومصمم UX/UI وخبير تكاملات OAuth وواجهات Meta وPayPal. مهمتك بناء منصة ويب مدفوعة لتحليل حسابات Instagram وFacebook بمساعدة الذكاء الاصطناعي، وإنتاج تقرير مفهوم وخطة محتوى عملية لمدة 30 يوماً.

اسم المشروع مؤقتاً: **[اسم المنصة يُحدد لاحقاً]**.

المنصة ليست أداة عامة لكتابة المنشورات فقط. إنها منتج SaaS يربط المستخدم بحساباته الاجتماعية بموافقته، يجمع البيانات التي تسمح بها الواجهات الرسمية، يحللها، ويقدم توصيات قابلة للتنفيذ مع توضيح حدود البيانات والتوقعات.

**مهم جداً:**
- لا تكتب أو تعرض أن المنصة تضمن الوصول إلى عدد معين من المشاهدات أو الزيارات أو المتابعين.
- لا تختلق بيانات أو Insights أو صلاحيات API غير متاحة.
- لا تستخدم scraping أو كلمات مرور المستخدمين أو جلسات المتصفح للوصول إلى الحسابات.
- لا تطلب كلمة مرور Instagram أو Facebook داخل موقعنا.
- لا تبدأ بكتابة المشروع كاملاً دفعة واحدة. ابدأ بمراجعة المتطلبات، ثم خطة معمارية، ثم مراحل تنفيذ قابلة للاختبار.
- عند وجود قرار تجاري غير محسوم، سجّله كسؤال مفتوح ولا تخترع قيمة أو سياسة.

# 2. ملخص المنتج

منصة ويب ثنائية اللغة:
- العربية هي اللغة الافتراضية، مع دعم RTL كامل.
- الإنجليزية مع دعم LTR كامل.
- الخط الأساسي في كامل المنصة: **Cairo**، مع أوزان مناسبة للعناوين والنصوص والأزرار.
- تصميم Responsive للهواتف والأجهزة اللوحية والحواسيب.
- يوجد حساب مستخدم ولوحة تحكم، وربط حسابات اجتماعية، ومحافظ محاولات، وشراء باقات، وتحليلات AI، وخطة محتوى، وسجل تحليلات، ولوحة إدارة كاملة.

يسمح حساب المستخدم بربط:
- حتى 5 حسابات Instagram.
- حتى 5 أصول/حسابات Facebook مدعومة رسمياً عبر Meta، مثل الصفحات التي يمنح المستخدم صلاحية إدارتها. لا تفترض أن واجهة Meta تمنح تحليلات للملفات الشخصية الشخصية العادية.

يجب أن يكون ربط الحسابات عبر تدفق OAuth الرسمي من Meta، مع طلب أقل مجموعة صلاحيات لازمة، وشرح سبب كل صلاحية، وإتاحة فصل الاتصال وسحب الوصول.

## 3.2 الخطوط والطباعة

- الخط الإلزامي: **Cairo** في كل الصفحات والعناصر والحقول والجداول والرسوم والتقارير.
- استخدم أوزان 400 للنصوص، 500/600 للعناوين الفرعية، و700 للعناوين الرئيسية عند الحاجة.
- لا تستخدم خطوط serif أو خطوطاً بديلة من ملف المرجع.
- تأكد من تحميل الخط محلياً أو من مصدر موثوق مرخص، مع fallback مناسب.
- اختبر الأرقام العربية والإنجليزية، علامات الترقيم، النصوص المختلطة، واتجاه النصوص.
- لا تضع نصوص الواجهة كصور.

## 3.3 الشكل العام

- أسلوب SaaS تحريري دافئ، بسيط، أنيق واحترافي.
- عرض المحتوى الرئيسي بحد أقصى تقريبي 1200px على الشاشات الواسعة.
- نظام مسافات مبني على مضاعفات 4px.
- نصف قطر الأزرار والحقول قرابة 8px، البطاقات 12–16px.
- حدود دقيقة بدلاً من الظلال الثقيلة.
- انتقالات قصيرة وهادئة، مع احترام `prefers-reduced-motion`.
- أيقونات SVG متناسقة من مكتبة واحدة؛ لا تستخدم Emoji كأيقونات للواجهة.
- لا تستخدم نصوصاً تجريبية مثل Lorem ipsum في المنتج النهائي.
- كل زر ورابط وتبويب يجب أن يؤدي وظيفة حقيقية، ولا تنشئ عناصر شكلية غير فعالة.

## 3.4 الاستجابة وإمكانية الوصول

- Mobile-first.
- هاتف: قائمة جانبية تتحول إلى Drawer أو قائمة مناسبة للمس، والجداول تتحول إلى بطاقات/تمرير أفقي مدروس.
- Tablet: تخطيط عمودين عند الحاجة.
- Desktop: Sidebar ثابتة للوحة التحكم مع Topbar.
- جميع أهداف اللمس واضحة ومناسبة.
- دعم لوحة المفاتيح، focus states، labels، رسائل أخطاء مفهومة، وتباين ألوان مناسب.
- RTL/LTR حقيقي على مستوى التخطيط والمكونات، وليس مجرد محاذاة النص.

## 7.1 قواعد Meta التقنية والأمنية
- اتبع أحدث وثائق Meta الرسمية وقت التنفيذ؛ لا تعتمد على أسماء صلاحيات قديمة أو أمثلة قديمة.
- تحقق من متطلبات Meta App Review وBusiness Verification وAdvanced Access عند انطباقها.
- اطلب أقل صلاحيات لازمة فقط، واشرحها للمستخدم.
- خزّن access tokens مشفرة في الخادم، ولا تعرضها للمتصفح أو السجلات.
- تعامل مع انتهاء الصلاحية، إلغاء التفويض، نقص الصلاحيات، rate limits، والأخطاء.
- نفّذ آلية Data Deletion Callback/طلبات حذف بيانات Meta عندما تكون مطلوبة.
- لا تستخدم scraping أو scraping عبر المتصفح أو APIs غير رسمية.
- لا تفترض توفر Insights لحساب Instagram شخصي عادي.
- بالنسبة إلى Facebook، لا تفترض توفر Insights للملف الشخصي الشخصي؛ اعمل فقط مع الصفحات/الأصول والصلاحيات المدعومة رسمياً.
- لا تعرض بيانات لا تسمح بها API أو لم يمنحها المستخدم.
- اكتب طبقة Adapter مستقلة لكل منصة حتى لا تختلط حقول Instagram وFacebook.
- وثّق لكل مؤشر مصدره، وتاريخ جلبه، والفترة الزمنية، وما إذا كان مباشراً أو محسوباً.

# 9. PayPal API والدفع

استخدم تكامل PayPal الرسمي فقط:
- PayPal REST API / Checkout Orders API وفق أحدث وثائق PayPal.
- إنشاء الطلب من الخادم وليس من المتصفح.
- اعتماد العملة ومبالغ التحصيل بعد تأكيد صاحب المشروع؛ لا تفترض أن سعر الشيقل يساوي مبلغ دولار ثابتاً.
- اعرض السعر المحلي بالشيقل، واعرض مبلغ وعملة التحصيل بوضوح قبل تأكيد الدفع.
- Visa تكون متاحة من خلال تجربة PayPal Checkout إذا كانت مؤهلة ومتاحة في بلد التاجر/المشتري وإعدادات PayPal؛ لا تعد المستخدم بتوفرها دائماً.
- لا تخزن أرقام البطاقات أو CVV.
- خزّن مفاتيح PayPal في Environment Secrets فقط.
- استخدم Sandbox في التطوير وLive بعد الاختبارات والموافقة.
- تحقق من الدفع من الخادم عبر capture/status والتحقق من توقيع Webhook وفق وثائق PayPal.
- لا تضف الرصيد بمجرد رجوع المستخدم إلى صفحة success.
- اجعل معالجة Webhook idempotent لمنع إضافة الرصيد مرتين.
- تحقق من العملة والمبلغ ومعرف الطلب وحالة الالتقاط قبل إضافة المحاولات.
- عالج pending، failed، cancelled، refunded، disputed/chargeback وفق حالات موثقة.
- أنشئ صفحات نجاح الدفع وإلغائه وفشله، مع تحديث الرصيد بعد التأكيد الحقيقي فقط.
- سجّل Payment ID وOrder ID والحالة والتوقيت دون تخزين معلومات بطاقة حساسة.

**أسعار الشيقل ثابتة وفق الاتفاق، أما مبالغ التحصيل بالدولار وآلية التحويل فلم تُحسم بعد. لا تضع أرقام USD نهائية من عندك.**

أنشئ تدفقاً واضحاً:
1. المستخدم يختار المنصة: Instagram أو Facebook.
2. يختار حساباً/صفحة مربوطة.
3. يرى الرصيد المتاح ونوع العملية التي ستستهلك محاولة.
4. يضغط بدء التحليل.
5. تظهر شاشة تقدم حقيقية بمراحل مفهومة، لا مؤشرات وهمية.
6. يجلب الخادم البيانات المتاحة من API.
7. يتحقق من اكتمال البيانات وجودتها.
8. يشغل محرك التحليل.
9. ينشئ التقرير وخطة المحتوى.
10. يحفظ النتيجة ويعرضها في سجل التحليلات.

قبل التنفيذ، تحقق من توفر رصيد. إذا لا يوجد رصيد، وجّه المستخدم إلى باقة المنصة الصحيحة. إذا فشلت العملية قبل اكتمالها، أعد المحاولة إلى الرصيد أو لا تخصمها أصلاً.

# 11. محرك التحليل AI

أنشئ محرك تحليل قابل للتوسع باستخدام Provider abstraction، حتى يمكن تغيير مزود AI دون إعادة بناء المنتج.

## 11.1 بيانات التحليل
استخدم فقط البيانات التي توفرها Meta رسمياً والتي يملك التطبيق صلاحية قراءتها، مثلما تسمح الوثائق الحالية:
- معلومات الحساب الأساسية المتاحة.
- بيانات المتابعين/الجمهور المتاحة.
- الوصول والمشاهدات والتفاعلات.
- أداء المنشورات وReels والقصص عندما تكون متاحة.
- بيانات التفاعل بحسب الفترة.
- نمو الحساب إذا كانت البيانات التاريخية متاحة.
- أوقات النشر/نشاط الجمهور إذا كانت متاحة.
- بيانات الصفحة ومحتواها وInsights المتاحة في Facebook.

إذا لم تتوفر بيانات تاريخية كافية، قل ذلك بوضوح ولا تستنتج نمواً تاريخياً غير موجود.

## 11.2 محتويات التقرير
يجب أن يتضمن التقرير:
- ملخصاً تنفيذياً.
- درجة أداء من 100 مع شرح طريقة الحساب ومكوناتها، لا رقم اعتباطي.
- نقاط القوة.
- نقاط الضعف.
- الفرص.
- المخاطر.
- تحليل أنواع المحتوى.
- أفضل المنشورات أداءً مع تفسير مدعوم بالأرقام.
- المحتوى الأقل أداءً مع تفسير حذر.
- تحليل انتظام النشر.
- تحليل التفاعل والوصول والمشاهدات.
- تحليل الجمهور عندما تسمح البيانات.
- توصيات عملية مرتبة حسب الأولوية.
- ما البيانات الناقصة التي تمنع حكماً أدق.
- نطاق زمني واضح لكل مؤشر.
- مصدر كل معلومة: Meta API أو حساب/مؤشر مشتق أو تقدير AI.

## 11.3 التوقعات التقديرية
يمكن أن يقدم النظام سيناريوهات نمو/وصول تقديرية، لكن:
- لا تعرض نطاق 100 ألف إلى مليون زيارة على أنه نتيجة مضمونة.
- لا تعرض توقعات ضخمة افتراضية بلا أساس.
- استخدم سيناريو محافظ/متوسط/متفائل فقط عند وجود بيانات تاريخية كافية.
- اذكر الافتراضات، والفترة، ومجال عدم اليقين.
- ميّز بوضوح بين الوصول والمشاهدات والزيارات والنقرات والمتابعين؛ هذه ليست مؤشرات متطابقة.
- إذا لم توجد بيانات كافية، اعرض "لا توجد بيانات كافية لتوقع موثوق" بدلاً من اختراع رقم.
- لا تستخدم لغة توحي بضمان الانتشار أو viral reach.

## 11.4 قواعد جودة AI
- لا تخترع أرقاماً أو أسباباً غير مدعومة.
- لا تستنتج معلومات حساسة عن الجمهور.
- لا تدّع معرفة خوارزمية Instagram أو Facebook الداخلية.
- استخدم لغة احتمالية عند تفسير العلاقة بين المحتوى والنتائج.
- اربط كل توصية بمؤشر أو ملاحظة محددة.
- أظهر مستوى الثقة: مرتفع/متوسط/منخفض، مع سبب.
- احتفظ ببيانات المصدر منفصلة عن نص AI.
- اجعل المخرجات قابلة للتحقق والمراجعة.

# 12. خطة محتوى لمدة 30 يوماً

بعد التحليل الأساسي، أنشئ خطة لمدة 30 يوماً مخصصة للحساب:
- تاريخ/اليوم.
- نوع المحتوى: Reel، منشور، Carousel، Story أو صيغة مدعومة.
- الفكرة.
- الهدف التسويقي.
- Hook أو افتتاحية مقترحة.
- ملخص السيناريو أو النقاط.
- CTA.
- اقتراح Caption.
- هاشتاغات مقترحة عند فائدتها، دون حشو.
- سبب اختيار الفكرة وربطها بنتائج التحليل.
- ملاحظات إنتاجية.
- توقيت مقترح فقط إذا كانت بيانات الحساب تدعمه؛ وإلا اكتب أنه اقتراح عام يحتاج اختباراً.

ميزات الخطة:
- عرض Calendar شهري.
- عرض قائمة تفصيلية.

- إمكانية تنزيل الخطة PDF/CSV إذا كانت التقنية المختارة تدعم ذلك.
- إمكانية حفظ الخطة والرجوع إليها.
- لا تنشر تلقائياً على حسابات المستخدم في الإصدار الأول ما لم يتم اعتماد ذلك وصلاحياته رسمياً.

# 13. المحاولات التكميلية بعد التحليل

يجب أن تبقى الحدود التي اتفق عليها صاحب المشروع ظاهرة وقابلة للتعديل من لوحة الإدارة:

1. مرحلة التحليل الأساسي مع خطة 30 يوماً.
2. سؤال متابعة إضافي بحد أقصى **500 حرف**.
3. دردشة احتياطية/إضافية بحد أقصى **3000 حرف**.

**يجب عدم افتراض أن السؤال والدردشة مجانيان أو تحديد طريقة خصمهما من الرصيد دون اعتماد تجاري نهائي.** أنشئ إعدادات إدارية لتحديد استهلاك كل نوع من المحاولات، واعرض سياسة الاستهلاك للمستخدم قبل الإرسال. لا تسمح بتجاوز حدود الأحرف من الواجهة أو الخادم.

10. **المدفوعات والفواتير**

11. **الإشعارات**

- دقة ربط التقرير بالحساب الصحيح.

# 22. مراحل التنفيذ المطلوبة من OpenCode

نفّذ بهذا الترتيب، ولا تنتقل للمرحلة التالية قبل تقرير إنجاز واختبارات المرحلة الحالية:

1. **Discovery:** فحص المستودع والملفات والبيئة وتحديد الموجود والناقص.
2. **Requirements:** تحويل الوثيقة إلى متطلبات وظيفية وغير وظيفية، وإخراج قائمة الأسئلة المفتوحة.
3. **Architecture:** اقتراح Stack ومخطط معماري وقاعدة بيانات وتدفقات OAuth والدفع.
4. **Design System:** إنشاء tokens ومكونات Cairo وRTL/LTR والصفحات الأساسية.
5. **Public Website:** صفحات التسويق والتعريف والأسعار والسياسات.
6. **Authentication:** التسجيل والدخول وإدارة الحساب.
7. **Social Connections:** Meta OAuth والاتصالات وإدارة الحسابات.
8. **Wallet & Pricing:** المحافظ والـ Ledger والباقات.
9. **PayPal:** Sandbox أولاً ثم Webhooks والاختبارات.
10. **Analysis Pipeline:** جمع البيانات والتحقق منها وتطبيعها.
11. **AI Reports:** التقرير والتوصيات والدرجات التفسيرية.
12. **30-Day Planner:** خطة المحتوى والتقويم والتصدير.
13. **Follow-up & Chat:** السؤال 500 حرف والدردشة 3000 حرف وفق سياسة الاستهلاك المعتمدة.
14. **User Dashboard:** استكمال كل صفحات المستخدم.
15. **Admin Dashboard:** الإدارة والصلاحيات والسجلات.
16. **Security & QA:** اختبارات أمنية ووظيفية وتجربة مستخدم.
17. **Deployment:** إعداد بيئات staging/production والنسخ الاحتياطي والمراقبة.

بعد كل مرحلة قدم:
- ما تم إنجازه.
- الملفات/الوحدات التي تغيرت.
- الاختبارات التي نجحت وفشلت.
- المخاطر أو القرارات المفتوحة.
- الخطوة التالية المقترحة.

# 23. قائمة القرارات المفتوحة — لا تخترع إجاباتها

قبل تفعيل الدفع والإطلاق، اطلب من صاحب المشروع اعتماد:
1. الاسم النهائي والشعار والدومين.
2. Stack النهائي والاستضافة وقاعدة البيانات.
3. مزود AI والنموذج وحدود التكلفة.
4. مبالغ PayPal بالدولار لكل باقة، مقابل أسعار العرض بالشيقل.
5. هل المحافظ منفصلة لكل منصة نهائياً؟ (الافتراضي المقترح: محفظة Instagram ومحفظة Facebook منفصلتان).
6. كيف تُستهلك المحاولات الثلاث الأولى: هل التحليل فقط يستهلك محاولة، أم سؤال المتابعة والدردشة أيضاً؟ وما آلية إعادة المحاولة؟
7. هل التقرير القديم يبقى متاحاً دائماً؟ (الاقتراح: نعم، ما لم يطلب المستخدم الحذف أو تفرض سياسة الاحتفاظ خلاف ذلك).
8. هل تسمح المنصة بتغيير الحساب الاجتماعي المرتبط بتحليل قديم؟ (الاقتراح: التقرير يظل مرتبطاً بالحساب ومجموعة البيانات وقت التحليل).
9. ما مدة الاحتفاظ بالبيانات الخام والـ Tokens وسجلات التحليل؟
10. متطلبات التسجيل التجاري والضرائب والفواتير وسياسة الاسترداد في بلد تشغيل الخدمة.

# 24. أول أمر تنفيذي منك الآن

لا تبدأ بإنشاء الملفات أو كتابة الكود مباشرة.

ابدأ بإخراج:
1. ملخص فهمك للمنصة.
2. خريطة صفحات كاملة.
3. خريطة تدفقات المستخدم والدفع والربط والتحليل.
4. اقتراح المعمارية التقنية.
5. مخطط قاعدة البيانات الأولي.
6. قائمة المخاطر والقيود الرسمية لـ Meta وPayPal التي يجب التحقق منها من الوثائق الحالية.
